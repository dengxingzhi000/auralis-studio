## 结论一：FFT 绝对不能放进音频回调

48 kHz 下每个回调周期的预算约 `1e6 / 48000 ≈ 20.8 µs`。

| 操作 | 中位数 | 预算倍数 |
|---|---|---|
| FFT 4096 | 271 µs | **13.0 倍** |
| FFT 1024 | 77 µs | 3.7 倍 |
| 峰值检测（2049 bins） | 65 µs | 3.1 倍 |

即使最小的 1024 点 FFT 也超预算 3.7 倍。

**这确认了 ADR-018 的架构**：音频回调只做「拷贝样本 + 计数」，
所有 FFT / 峰值检测 / STFT 都在工作线程上跑。
这不是「保守起见」，是**测量结论**。

> 唯一的例外是频谱降采样到 800 点（19.8 µs）勉强在预算内，
> 但它依赖上游已有频谱数据，回调里并不存在这样的数据。
> 不应据此认为回调可以承担任何 DSP。

## 结论二：一个未能达标的既有目标

`docs/superpowers/specs/2026-10-14-auralis-studio-design.md` §7.5 曾写
「FFT 4096 点（Release，单次）< 100 µs」。

**实测 271 µs，未达标（2.7 倍）。**

该目标是在没有任何测量的情况下写下的估算值。现在有了实测，
应以本文件为准。需要更低延迟时应考虑：预分配 plan（已做）、
实数 FFT（`realfft`，M2 已验证可解析 6.4 同系）、或 SIMD（`wide` / `core::arch`）。
**目前不宣称 FFT 达到任何既定性能指标。**

## 结论三：离线分析吞吐是够的

`stft_2048_512_1s` = 3.47 ms/秒音频 ⇒ 实时率约 **290 倍**。
`stft_range` 0.1 秒 = 264 µs ⇒ **视口分块重算也足够快**
（M4 的分块方案在性能上成立）。

## 实时采集实测（2026-10-22）

同一台机器上的真实 WASAPI 输入（不是合成信号）：

| 项 | 值 |
|---|---|
| 设备 | Realtek WASAPI 默认输入，2 声道，48 kHz |
| 命令 | `node scripts/check-capture.mjs --seconds 6` |
| 采集时长 | 6.03 s |
| 处理帧数 | 287,040（**0.991 × 实时**） |
| 环形缓冲丢帧 | **0** |
| 快照大小 | 4,096 B（1024 bin × f32） |
| 轮询频率 | 约 26.5 Hz（33 ms 间隔） |
| 快照 RPC 往返 | **p50 0.33 ms / p95 3.10 ms / max 4.45 ms** |
| 峰值 / RMS 范围 | −165.0…−15.0 / −174.9…−35.1 dBFS |
| 引擎警告 / 错误 | 0 / 0 |

**结论四：30 Hz 轮询足够，不需要第二通道。**
4 KB × 60 Hz 约 240 KiB/s（base64 后约 320 KiB/s），实测 p95 只占
33 ms 周期的 9%。这条数据是 [ADR-020](ADR.md#adr-020实时高频通道与-asio-评估)
关闭「高频通道」决策的直接依据。

> 该延迟只覆盖「Node 宿主 ↔ stdio 引擎」，不含 Electron 主进程到渲染进程的
> 结构化克隆和 Canvas 绘制。它证明的是**引擎侧 + 传输载荷不是瓶颈**，
> 不是整条 UI 帧时间的上限。

## 容器全链路实测（2026-10-23，release 引擎）

回答「加上 Electron 主进程 → 渲染进程这一段之后还剩多少开销」。
方法：真实窗口中通过 `window.auralis.invoke` 调用，在渲染进程内用
`performance.now()` 计时（不含 CDP 往返）；同一文件同一命令再用
`direct-rpc.mjs` 直连引擎 stdio 对照。

| 负载 | 经 Electron 全链路 | 直连引擎 stdio |
|---|---|---|
| `app_info` | 4.9 ms（中位数） | 0.3 ms |
| `probe_file` | 1.5 ms（中位数） | 1.2 ms |
| `input_devices` | 6.8 ms（中位数） | — |
| `analyze_file`，900 s / 48 kHz / 立体声（172.8 MB） | **5.9 s** | **6.1 s（冷）/ 3.9 s（页缓存热）** |

结论：**容器与 IPC 不是文件分析的瓶颈**。900 秒音频的分析耗时由解码 +
STFT 决定，两条路径的差异落在采样噪声内。载荷方面，该次响应包含
2.8 MB 声谱图（base64 后约 3.7 MB），结构化克隆的代价仍低于一次
`analyze_file` 的总耗时。

> 限制：以上是单机、单次采样，不是统计意义上的基准；首次调用含引擎冷启动，
> 已从快命令中位数里排除。
